PyTorch: under the hood

Layers 1–4 derived the equations; this is the workshop where they run. Tensors and the stride trick, the autograd tape, modules and optimizers, the CUDA execution model, torch.compile — plus the ecosystem of tools around them. Not just how to call the API: how the machine underneath actually works.

Scroll to begin · 8 chapters

PyTorch won research because it commits to one idea: a neural network is just a Python program. Tensors are values, layers are objects, training is a for-loop you can print from and step through in a debugger. But beneath that friendly surface sits serious machinery — a memory model that makes transposes free, a gradient tape recording every operation, an asynchronous GPU queue, and a compiler. Knowing the machinery is what separates "I can run the tutorial" from "I can fix it at 2 a.m. when the loss is NaN." Every concept links back to where its math was built in Layers 1–4.

How to read this

Dark panels are code — real, runnable PyTorch. Blue panels are definitions; green panels build intuition; black-edged panels are derivations (yes, systems have derivations too); coral elements are interactive — several demos implement the actual internals (a stride engine, a gradient tape) in your browser so you can watch them work.

Chapter 01

Tensors & Memory

Everything in PyTorch is a tensor: Layer 1's vectors and matrices, made executable, with two extra coordinates the math never mentioned — a dtype and a device. Understanding how a tensor actually sits in memory explains half of PyTorch's surprising behaviors, and makes the other half predictable.

1.1 · The tensor object

import torch

x = torch.tensor([[1., 2., 3.],
                  [4., 5., 6.]])        # 2×3 matrix (Layer 1, Ch 2)
x.shape      # torch.Size([2, 3])
x.dtype      # torch.float32  — 4 bytes per number
x.device     # cpu             — or cuda:0, mps, ...

torch.randn(32, 3, 224, 224)             # a batch of images: N×C×H×W
torch.zeros(10, dtype=torch.long)        # integer tensors for indices/labels
x.to("cuda")                             # copy to GPU (returns a NEW tensor)

A tensor is an n-dimensional array plus bookkeeping. The dtype sets precision and cost (float32 default; bfloat16 for speed, Ch 5; long for indices). The device says which processor's memory holds the bytes — and operations require all operands on the same device, the source of the beloved Expected all tensors to be on the same device error.

1.2 · Storage & strides — the trick behind free transposes

Definition — storage + strides

A tensor is a view onto a flat 1-D storage buffer, described by three numbers per dimension: shape, stride (how many storage slots one step along that dimension jumps), and a storage offset. The element at index $(i_0,i_1,\dots)$ lives at:

$$\text{position}=\text{offset}+\sum_{d} i_d\cdot \text{stride}_d$$

A fresh $4\times6$ tensor is row-major: strides $(6,1)$ — step a row, jump 6 slots; step a column, jump 1.

Derivation — why transpose costs nothing and view sometimes refuses
1

Transpose = swap the strides. $x^{\top}[i,j]=x[j,i]$ means position $=j\cdot6+i\cdot1$ — which is just the same storage read with strides $(1,6)$ and shape $(6,4)$. Zero bytes move. The same trick powers slicing: x[:, 1:5:2] is offset 1, strides $(6,2)$. Indexing arithmetic replaced copying — this is why slicing huge tensors is instant.

2

The price: the storage is now visited out of order — the tensor is no longer contiguous. .view() only re-labels shape/strides assuming row-major layout, so on a transposed tensor it raises the famous error; .reshape() or .contiguous() quietly performs the real copy that re-packs memory.

3

Corollary that bites everyone once: views share storage. Write through a slice and the original changes too. (NumPy interop inherits this: torch.from_numpy(a) wraps the same buffer — fast precisely because nothing is copied.)

Interactive

Hover any cell of the logical tensor (top) and watch the stride formula light up its true home in the flat storage (bottom). Switch views: the logical grid reshapes, strides change, the storage never moves. x.T walks the buffer column-wise — same 24 floats, different walking order. This one picture is the mental model behind view/reshape/contiguous/permute and most "why is this slow" mysteries.

1.3 · Broadcasting — stride 0, the free expansion

Definition — broadcasting rules

When shapes differ, align them from the right; dimensions match if equal or if either is 1; size-1 dimensions are (virtually) stretched. $(4,1,6)+(3,1)\to(4,3,6)$.

Intuition — and the under-the-hood punchline

How does PyTorch "stretch" a size-1 dimension without allocating? Stride 0. Stepping along that dimension jumps zero slots — every index reads the same element. Broadcasting is the stride trick at its most elegant: an illusion of a bigger tensor, manufactured purely in the index arithmetic. (It is also a bug factory: add a $(N,)$ vector to a $(N,1)$ column and you silently get $(N,N)$ — when training is mysteriously wrong, print your shapes first. Chapter 8's quiz drills exactly this reflex.)

Chapter 02

Autograd: The Tape

Layer 1 derived the chain rule; Layer 2 turned it into backpropagation. Autograd is that mathematics as infrastructure: every operation you run is silently recorded on a tape, and backward() plays the tape in reverse. This chapter opens the recorder.

2.1 · The dynamic graph

x = torch.tensor(2.0, requires_grad=True)
w = torch.tensor(3.0, requires_grad=True)
b = torch.tensor(1.0, requires_grad=True)

y = (w * x + b).relu() ** 2     # forward pass — and the recording

y.grad_fn                        # <PowBackward0>
y.grad_fn.next_functions         # (<ReluBackward0>, ...) — the tape, exposed

y.backward()                     # play the tape in reverse
x.grad, w.grad, b.grad           # tensor(42.), tensor(28.), tensor(14.)

Each operation on a requires_grad tensor creates a node holding (1) a backward function — the local derivative rule — and (2) saved tensors, the forward values that rule will need (this is where activation memory goes, and what gradient checkpointing trades for recompute). The graph is dynamic: built fresh by simply running Python, so loops, branches, and print() all just work — the property that won researchers over.

2.2 · Why reverse mode — one pass, all gradients

Derivation — the asymmetry that makes deep learning affordable
1

A network is $f:\R^{n}\to\R$ — millions of parameters in, one loss out. The chain rule (Layer 1, Ch 3) composes Jacobians; the only question is the order of multiplication.

2

Forward mode carries a directional derivative along with the computation: one pass yields $J\mathbf{v}$ — the sensitivity to one input direction. Recovering all $n$ partials needs $n$ passes. At $n=10^9$ parameters: dead on arrival.

3

Reverse mode propagates from the output backward, computing the vector–Jacobian product $\mathbf{u}^{\top}J$ in one pass. For a scalar loss, $\mathbf{u}=1$ and that single product is the entire gradient — all $n$ partials for roughly one extra forward's cost. The shape of the problem (many→one) picks the direction of differentiation. That is why training giant models is possible at all, and why each node stores a VJP rule: upstream-gradient in, local-Jacobian-transpose times it, out.

2.3 · Rules of the tape

with torch.no_grad():            # don't record: inference, metric computation
    preds = model(x)

z = y.detach()                    # same data, severed from the graph
loss.item()                       # python float — also a GPU sync point (Ch 5!)

x += 1                            # in-place on a recorded tensor: autograd may raise —
                                  # a saved tensor was modified; version counters catch it

Three rules cover daily life. (1) Gradients accumulate — by design (shared weights legitimately receive multiple contributions), so the training loop must zero them. (2) What isn't recorded can't backprop: no_grad/detach are how you say "this path is not part of learning" (the EMA teachers of Layer 3 and target networks of Layer 4 live behind no_grad). (3) Don't mutate what the tape saved — in-place ops on tensors needed for backward trip a version-counter error, autograd's tamper seal.

Chapter 03

Modules & Optimizers

Above the tape sits the part of PyTorch everyone meets first: nn.Module, losses, optimizers. They look like magic containers; they are three small, inspectable mechanisms.

3.1 · nn.Module — a parameter registry with a forward()

class Linear(nn.Module):                       # nn.Linear, reimplemented
    def __init__(self, n_in, n_out):
        super().__init__()
        self.W = nn.Parameter(torch.randn(n_out, n_in) * n_in**-0.5)
        self.b = nn.Parameter(torch.zeros(n_out))
    def forward(self, x):
        return x @ self.W.T + self.b              # Layer 2, Ch 1 — one layer

model = nn.Sequential(Linear(784, 256), nn.ReLU(), Linear(256, 10))
sum(p.numel() for p in model.parameters())     # 203,530
model.state_dict().keys()                          # '0.W', '0.b', '2.W', '2.b'
Under the hood — the __setattr__ trick

How does model.parameters() find every weight in an arbitrarily nested model with no registration code from you? nn.Module overrides Python's __setattr__: the moment you assign an nn.Parameter (or a sub-module) as an attribute, it is intercepted and filed into an internal _parameters/_modules dict. .parameters() just walks the tree of dicts; .state_dict() snapshots it as name → tensor (the checkpoint format — which is why renaming a layer breaks old checkpoints); .to(device), .train()/.eval() walk the same tree. One dunder method powers the whole module system.

One subtlety earns its keep daily: model(x) calls __call__, which runs hooks and dispatch around your forward() — so always call the module, never model.forward(x). And .eval() doesn't disable gradients; it flips behavior flags (dropout off, batch-norm uses running stats — Layer 2, Ch 2). Inference wants both .eval() and no_grad.

3.2 · Losses — and the log-sum-exp safety rail

Derivation — why cross_entropy refuses to let you softmax first
1

float32 overflows at $\approx3.4\times10^{38}$, and $e^{z}$ crosses that at $z\approx88.7$. Logits of ±90 — entirely normal mid-training — make a naive $\operatorname{softmax}=e^{z_i}/\sum e^{z_j}$ return inf/inf = nan, and one NaN gradient poisons every parameter in a single step.

2

The fix is an identity. For any constant $m$:

$$\log\sum_i e^{z_i}=\log\Big(e^{m}\sum_i e^{z_i-m}\Big)=m+\log\sum_i e^{z_i-m}$$

Choose $m=\max_i z_i$: every exponent becomes $\le0$, so every $e^{(\cdot)}\in(0,1]$ — overflow is impossible, and the math is exactly unchanged.

3

This is why F.cross_entropy takes raw logits and fuses log-softmax + NLL internally (Layer 1 Ch 8's cross-entropy, armored for float32), and why the cardinal API rule exists: never put a softmax before cross_entropy. Numerical safety in PyTorch is mostly "use the fused op that contains the identity."

Interactive

Watch float32 die — and log-sum-exp shrug

Slide the logits toward the cliff at $z\approx88.7$. The naive pipeline's $e^{z}$ shoots toward the float32 ceiling and detonates into inf → nan; the stabilized path computes the same value serenely at $z=150$, because after subtracting the max its biggest exponent is $e^{0}=1$. One algebra trick, production-critical.

3.3 · Optimizer anatomy

opt = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=0.01)

opt.param_groups[0].keys()    # params, lr, betas, eps, weight_decay ... (the dials)
opt.state[some_param]          # {'exp_avg': m, 'exp_avg_sq': v, 'step': t}  — Layer 2 Ch 2's
                               # Adam moments, living in a dict keyed by parameter

An optimizer is two dictionaries and a rule. param_groups holds parameter lists with their hyperparameters (multiple groups = different learning rates per part of the model — how fine-tuning freezes or slows a backbone). state holds per-parameter buffers: Adam's $m$ and $v$ are literally here, which is why optimizer checkpoints are ~2× model size and why resuming without them briefly destabilizes training. step() reads each p.grad and applies the update rule you derived in Layer 2 — nothing more mystical than a for-loop over the registry from 3.1. Schedulers just rewrite param_groups[i]['lr'] on a timetable.

Chapter 04

The Training Loop

Five lines repeat across all of deep learning — the same five whether the model is a linear probe or a 70B VLA. Here is the loop as a Rosetta stone, each line mapped to the layer that derived it, followed by the machinery that feeds it and the bugs that haunt it.

4.1 · The canonical loop, annotated

for xb, yb in loader:                       # minibatch ≈ sampled expectation   (L1 Ch5)
    xb, yb = xb.to(dev), yb.to(dev)

    logits = model(xb)                       # forward: matrices + nonlinearity  (L2 Ch1)
    loss = F.cross_entropy(logits, yb)       # NLL of a categorical              (L1 Ch8)

    opt.zero_grad()                          # the tape accumulates — clear it   (Ch 2)
    loss.backward()                          # reverse-mode chain rule           (L1 Ch3 → L2)
    opt.step()                               # gradient descent, refined         (L1 Ch3, L2 Ch2)

The entire curriculum, in seven lines of Python.

Evaluation wraps the forward in model.eval() + torch.no_grad(), and logging uses loss.item() — pulling a Python float out (and, as Chapter 5 explains, quietly synchronizing the GPU; log every N steps, not every step).

4.2 · Datasets & DataLoaders

class Demos(torch.utils.data.Dataset):     # e.g. robot demonstrations (L4 Ch7)
    def __len__(self): return len(self.episodes)
    def __getitem__(self, i):                # ONE example: load, decode, augment
        return self.obs[i], self.action[i]

loader = DataLoader(ds, batch_size=64, shuffle=True,
                    num_workers=8, pin_memory=True)

The division of labor: Dataset defines one example; DataLoader turns it into an industrial pipeline — shuffling (the i.i.d. assumption of Layer 1, enforced), batching via a collate function that stacks tensors, and worker processes. Workers are separate processes, not threads, because Python's GIL allows only one thread to run Python at a time; loading therefore overlaps with GPU compute. pin_memory puts batches in page-locked RAM so the host-to-GPU copy can run asynchronously (Ch 5). When the GPU sits idle, the dataloader is the suspect: starved GPUs, not slow models, are the most common training-speed bug.

Chapter 05

GPUs & the Execution Model

A GPU is not a faster CPU; it is a different bargain — thousands of slow workers instead of a few fast ones, profitable only when work comes in wide, regular slabs. PyTorch hides the machinery well enough that you can ignore it right up until you try to make anything fast. Two ideas explain almost everything: the roofline, and the queue.

5.1 · Why GPUs win — and when they don't

Derivation — arithmetic intensity, and the roofline law
1

Every kernel needs two resources: arithmetic (FLOPs) and memory traffic (bytes moved). Define arithmetic intensity $I=\text{FLOPs}/\text{bytes}$. Hardware supplies compute at peak $P$ (FLOP/s) and memory at bandwidth $B$ (bytes/s), so the achievable rate is whichever resource runs out first:

$$\text{attainable}=\min\big(P,\;B\cdot I\big)$$

— the roofline: a bandwidth-sloped ramp meeting a flat compute ceiling at the ridge $I^{\ast}=P/B$.

2

Now compute $I$ for the two workloads that matter. Elementwise add on $n$ floats: $n$ FLOPs, $12n$ bytes (two reads, one write, 4 B each) → $I=1/12$, hopelessly below any modern ridge: memory-bound, no matter the GPU. Matmul of $n\times n$: $2n^3$ FLOPs over $12n^2$ bytes → $I=n/6$, growing with size — big matmuls sail past the ridge into compute-bound paradise, which is precisely the regime tensor cores were built for.

3

The two corollaries that organize all performance work: (a) deep learning is fast because its core op is the one whose intensity scales; (b) everything around the matmuls — activations, norms, residual adds — is memory-bound, so the only cure is to move fewer bytes: fuse kernels (Ch 6) and shrink dtypes (5.3).

Interactive

The roofline — find the ridge, place your ops

The dots are real workloads at their intensities: elementwise ops pinned to the ramp's far left, matmul sliding right as $n$ grows. Drag $n$ down to 64 and watch even the GPU's favorite op go memory-bound — the small-batch / small-model regime where GPUs disappoint. Raise bandwidth and the ridge slides left, rescuing them. Every "why is my model slow" investigation starts by locating the workload on this picture.

5.2 · The async queue — your Python is just placing orders

t0 = time.time()
y = model(x)                       # returns almost instantly — kernels merely ENQUEUED
print(time.time() - t0)            # ~0 ms: you timed order-placement, not cooking

torch.cuda.synchronize()           # wait for the kitchen to actually finish
loss.item()                        # needs the real number → implicit synchronize

CUDA calls are asynchronous: Python enqueues kernels onto a stream and races ahead; the GPU consumes the queue at its own pace. This is a feature — CPU-side Python overhead hides behind GPU work — but it makes naive time.time() measurements lies, and it means every .item(), .cpu(), or print of a GPU value is a sync point that stalls the pipeline. The classic slow-training culprit isn't compute; it's a metric logged every step draining the queue.

Interactive

The queue — async pipelining vs. a sync point every step

Top lane: CPU (Python) launching work. Bottom: GPU executing it. Async, the CPU sprints ahead and the GPU runs wall-to-wall. Add a sync every step and the lanes must rendezvous: bubbles appear on both, and the same eight steps take visibly longer. The fix costs nothing — accumulate metrics on-GPU, sync once per hundred steps.

5.3 · Mixed precision

with torch.autocast("cuda", dtype=torch.bfloat16):
    loss = F.cross_entropy(model(xb), yb)     # matmuls in bf16, reductions in fp32
loss.backward()

Half-precision halves every byte moved — a direct 2× on the memory-bound ramp, plus tensor cores run low-precision matmuls several times faster. The catch is range: float16's tiny exponent underflows small gradients to zero, requiring the GradScaler loss-scaling dance. bfloat16 keeps float32's full exponent range by sacrificing mantissa — gradients survive, no scaler needed — which is why bf16 autocast is the modern default and fp16 a legacy mode. (Inference pushes further: int8/fp8 quantization, Layer 6 territory for fitting VLAs onto robot-side hardware.)

Chapter 06

torch.compile — Eager Code, Compiled Speed

PyTorch's superpower — it's just Python — is also its tax: the interpreter dispatches one kernel at a time, blind to the next line. torch.compile (PyTorch 2.x) removes the tax without removing the Python: it watches your function run, captures what it does, and rebuilds it as fused machine code. One line, and the compiler stack below wakes up.

6.1 · The stack: Dynamo → AOTAutograd → Inductor

model = torch.compile(model)        # that's the whole API

# Under the hood, three machines:
# 1. Dynamo      — hooks CPython bytecode, traces tensor ops into an FX graph,
#                  installs GUARDS (shapes, dtypes); re-traces if a guard fails
# 2. AOTAutograd — runs the tape logic of Ch 2 AHEAD of time → a backward graph too
# 3. Inductor    — fuses ops and emits Triton kernels (GPU) / C++ (CPU)
Intuition — a stenographer, not a straitjacket

Dynamo solves the problem that killed earlier attempts (TorchScript asked you to rewrite code in a Python subset): it captures the program by watching the real interpreter run it, at the bytecode level. Lines it can't capture — a print, an .item(), control flow that branches on a tensor's value — don't crash anything; they cause a graph break: the compiled region ends, plain Python handles the odd line, a new compiled region begins. Guards are the honesty mechanism: the captured graph assumed your batch was 64×784 float32, so cheap shape/dtype checks run each call, and a violation triggers recompilation. Your dynamic Python is still dynamic; you just pay compile cost the first time each variant runs — which is why compiled training feels slow for a step, then fast forever.

6.2 · Kernel fusion, quantified

Derivation — fusing k memory-bound ops buys ~k×
1

An elementwise chain — x.mul(a).add(b).relu(), the connective tissue between matmuls — runs as $k$ separate kernels in eager mode. Each reads $n$ elements from DRAM and writes $n$ back: total traffic $2kn$ elements, and Ch 5 proved these ops are memory-bound, so traffic is time.

2

A fused kernel loads each element once, does all $k$ operations in registers, writes once: traffic $2n$. Speedup:

$$\frac{2kn}{2n}=k$$

Three fused ops ≈ 3× on that segment, for free. (The celebrity case: FlashAttention is this idea applied inside attention — never materialize the $n\times n$ score matrix in DRAM — which is why it beats "optimized" eager attention by large factors.)

3

Inductor does this automatically — pattern-matching the FX graph, generating Triton kernels (a Python-syntax GPU language that has become the lingua franca of custom kernels), and autotuning tile sizes per shape and device. The compiler is doing roofline reasoning so you don't have to.

Interactive

Fusion economics — bytes moved, eager vs. compiled

Each block is one pass over the tensor in DRAM. Eager mode pays the round trip $k$ times; the fused kernel pays once. Slide $k$ up and watch the speedup track it linearly — then recall how many add / mul / norm / activation lines sit between the matmuls of a transformer block, and the headline "torch.compile made training 1.5–2× faster" stops being mysterious.

Chapter 07

The Ecosystem

Nobody trains a robot with PyTorch alone. Around the core sits a stack of tools — scientific, training, and robotic — each solving one layer of the problem. Here is the map, with the under-the-hood thread continued: most of these tools are thin, inspectable conventions over the mechanisms you now know.

7.1 · The scientific stack

import numpy as np
a = np.random.randn(1000, 1000)
t = torch.from_numpy(a)        # ZERO-copy: wraps the SAME buffer (Ch 1 strides!)
t[0, 0] = 99.0                  # ...so a[0,0] is now 99.0 too
back = t.numpy()                # zero-copy in reverse (CPU tensors only)

NumPy is the lingua franca PyTorch deliberately mirrors (same slicing, same broadcasting — Ch 1 was secretly a NumPy lesson too), and interop is free because both sides agree on the storage-plus-strides memory model. Around it: matplotlib for looking at everything (loss curves before dashboards, always), pandas for tabular wrangling, and einops — rearrange(x, 'b (h w) c -> b c h w', h=14) — which replaces error-prone view/permute chains with self-documenting shape algebra. Many ViT implementations (Layer 3) read better in einops than in math.

Intuition — and the honest contrast: JAX

PyTorch's worldview is imperative: run the program, record the tape (Ch 2). JAX — the other serious framework — is functional: write pure functions, and transformations (grad, jit, vmap) rewrite them; compilation isn't an add-on, it's the premise. JAX rewards you in large-scale and TPU settings and in research that composes transformations (meta-learning, per-sample gradients); PyTorch rewards debuggability and ecosystem gravity. Notice the convergence, though: torch.compile is PyTorch adopting JAX's bet, and both compile to the same class of fused kernels. The concepts in this book transfer wholesale.

7.3 · The robotics stack

import gymnasium as gym          # the MDP of Layer 4, as an API
env = gym.make("HalfCheetah-v5")
obs, info = env.reset()
for _ in range(1000):
    action = policy(torch.as_tensor(obs))    # your π_θ (L4 Ch5)

    if term or trunc: obs, info = env.reset()

The agent loop of Layer 4, as five lines. Around it: Stable-Baselines3 (reference PPO/SAC implementations — the Layer 4 algorithms, productionized), MuJoCo and Isaac Lab (the hand-built world models of Layer 4 Ch 8: physics simulators, with Isaac running thousands of environments in parallel on GPU for locomotion-scale RL), and LeRobot — Hugging Face's robotics library, where the policies this curriculum keeps citing (ACT, Diffusion Policy, π0-style VLAs) exist as trainable PyTorch code with shared dataset formats. For deployment, torch.export → ONNX / TensorRT compiles the policy for the robot-side computer (a Jetson, typically) — Layer 6's latency budgets, met with Chapter 5–6's tools.

Where you'll meet this again

When Layer 5 trains locomotion in simulation, the stack is Isaac + PPO-from-SB3-or-custom + this chapter's logging; when Layer 6 fine-tunes a VLA, it is LeRobot/transformers + FSDP + bf16 + torch.compile. Every line of those future chapters' tooling has now been introduced.

Chapter 08

Capstone — Reading Real Code

Here is a complete, modern training script — the kind you'll actually encounter — with every idea from this supplement in play. Read it slowly once; after this book it should feel less like an incantation and more like a checklist.

8.1 · A real script, annotated

import torch, torch.nn.functional as F
from torch.utils.data import DataLoader

dev    = "cuda" if torch.cuda.is_available() else "cpu"
model  = build_model().to(dev)                       # Ch 3: module tree → device
model  = torch.compile(model)                        # Ch 6: Dynamo+Inductor
opt    = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=0.01)
sched  = torch.optim.lr_scheduler.CosineAnnealingLR(opt, T_max=10_000)
loader = DataLoader(ds, batch_size=128, shuffle=True,
                    num_workers=8, pin_memory=True)  # Ch 4: feed the GPU

for step, (xb, yb) in enumerate(loader):
    xb = xb.to(dev, non_blocking=True)               # Ch 5: async H2D copy
    yb = yb.to(dev, non_blocking=True)

    with torch.autocast(dev, dtype=torch.bfloat16):  # Ch 5: mixed precision
        loss = F.cross_entropy(model(xb), yb)        # Ch 3: fused, LSE-stable

    opt.zero_grad(set_to_none=True)                  # Ch 2: the tape accumulates
    loss.backward()                                  # Ch 2: reverse-mode VJPs
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step(); sched.step()                         # Ch 3: registry + state dicts

    if step % 100 == 0:                              # Ch 5: don't sync every step
        print(f"step {step}  loss {loss.item():.4f}")
    if step % 1000 == 0:
        torch.save({"model": model.state_dict(),     # Ch 3: names → tensors
                    "opt":   opt.state_dict(),       # Adam moments live here too
                    "step":  step}, "ckpt.pt")

The whole supplement, in one paragraph

A tensor is a view over flat storage — strides make transposes free, stride-0 makes broadcasting free, and contiguity explains the rest. Every op writes to a tape; backward() replays it as vector–Jacobian products, accumulating into .grad — which is why you zero it. Modules are parameter registries caught by __setattr__; optimizers are two dicts and an update rule; losses hide the numerical identities (log-sum-exp) that keep float32 alive. The loop is seven lines, fed by worker processes. The GPU is an async queue obeying the roofline — move fewer bytes (fusion, bf16) and sync rarely. torch.compile watches your Python and does the byte-economics for you. Around it all, an ecosystem of thin conventions — and now none of it is magic.
